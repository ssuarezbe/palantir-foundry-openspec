Layout: `core/` (what every team copies), `addons/` (per-environment), `maintainer/` (build, test, provenance; not in the release zip), `docs/` (four guides). Top level also has `README.md`, `CHANGELOG.md`, `VERSION`, `LICENSE`, `THIRD_PARTY_NOTICES.md`.

Commands:
- `maintainer/tests/run-all.sh` — every check, offline. `--no-jest` skips the Jest part. Jest needs `maintainer/scripts/setup-test-env.sh` once on a connected machine (installs into the gitignored `maintainer/tests/jest-env/node_modules`).
- `maintainer/scripts/build.sh [--release]` — connected machine only: `npm ci --ignore-scripts` from the lock in `maintainer/scripts/pinned/` (the npm package has no lockfile; unpinned builds drift), `bun build`, two `sed` patches to the bundle (both fail the build if they don't match exactly once), hashes, licence texts into `addons/cli/`; `--release` writes the lean zip (top-level files, `docs/`, `core/`, `addons/`) and its SHA-256 next to the repo.
- `maintainer/scripts/sync-upstream.sh <version> [--write]` — regenerate `maintainer/upstream/generated/`; `--write` also reruns `maintainer/scripts/make-workspace.py`.
- `addons/workspace/` is generated by `make-workspace.py` from `maintainer/upstream/generated/`; don't hand-edit it. It keeps four workflows plus the `openspec-sync-specs` skill (the archive skill runs it inline; removing it breaks archive).
- The schema has one copy: `core/project-template/openspec/schemas/foundry-spec-driven/`.
- `maintainer/tests/fixtures/` was generated once; edit the files directly. Each fixture's `expected` file lists the expected bundle/jest/python result (`bundle=skip` for satellite repos) and a reason substring.
- Multi-repo model: one spec home (store), other repos declare `store: <id>` (`docs/multi-repo.md`). The store registry is per-machine; `run-all.sh` section 8 sets `XDG_DATA_HOME`/`XDG_CONFIG_HOME` to temp dirs so it never touches the real registry — do the same when experimenting.
- Gherkin: scenarios use GIVEN/WHEN/THEN/AND/BUT, tasks have `Verify:` lines. The rules live in the schema instructions and templates, `config.yaml` and `core/aip-skills/`; the only automatic check is OpenSpec's trigger-and-outcome rule (ported to the Python check).
- Tested only on Node 20.19.3 (OpenSpec declares `>=22.12.0`); nothing has run inside Foundry.

## What this project is

An internal, curated packaging of **OpenSpec `@fission-ai/openspec` 1.16.0** (MIT licensed, https://github.com/Fission-AI/OpenSpec) for teams building on Palantir Foundry inside a restricted, no-npm-access network. Output is a single Git repo a team can bring in via an approved transfer — not an official OpenSpec or Palantir product.

Three target environments, each needing a different delivery shape:
1. **AI FDE in Foundry** — no shell, no Node. Gets AIP skills (plain Markdown, zero CLI calls) loaded from a Compass folder.
2. **Foundry VS Code workspaces** — remote terminal, Continue extension, Palantir MCP. Gets `.continue/` config pointed at a launcher script.
3. **Laptops** (Win/macOS/Linux, VPN, Node maybe absent) — gets `.claude/` config and the bundled CLI.

CI gate: TypeScript functions repos run Jest on every commit; a Python standard-library port of the same validation rules exists for repos without Node.

## Architecture

- `core/project-template/` — what a new Foundry project starts from: `openspec/config.yaml` (schema + context + rules for glossary, Ontology, Gherkin), `openspec/glossary.md` template, the `foundry-spec-driven` schema (a fork of `spec-driven` adding Ontology references, glossary changes, Foundry resources, `Implemented in:`, Gherkin, plus the artifacts `ontology`, `data`, `logic` and `open-questions`; graph: **proposal → specs / design / ontology / data / open-questions; ontology → logic; all → tasks → apply**), empty `specs/` and `changes/archive/`.
- `core/aip-skills/` — four AIP skills (explore/propose/apply/archive), each a `Name:`/`Description:` + Markdown body, each under ~150 lines. Hard rule: **zero `openspec` CLI calls** in this directory — every step is written out manually. Enforced by a grep-based test.
- `addons/cli/` — `openspec-1.16.0/` (the bundle, `package.json`, `schemas/`; the bundle reads `package.json` two directories above itself, so don't flatten it; `bun build --compile` does not work), `launchers/` (sh and `.cmd`, always set `OPENSPEC_TELEMETRY=0`), `SHA256SUMS`, `PIN.md` (version, hashes, local patches), and the bundled-package licences.
- `addons/workspace/` — `.continue/` and `.claude/` generated from upstream output, CLI calls rewritten to `./tools/openspec/launchers/openspec`.
- `addons/ci/` — the Jest gate (`typescript/`) and its Python parity port (`python/`). Both skip themselves in a satellite repo (config has `store:`).
- `maintainer/upstream/` — untouched `init` output in `generated/` (diff baseline, never edit) and the upstream licence.
- `maintainer/tests/run-all.sh` — the single entry point that proves the repo: bundle integrity and hash agreement with `PIN.md`, schema validity, fresh-project validation, fixtures through bundle/Jest/Python with parity, store flow, the aip-skills CLI-call grep, launcher telemetry, and a URL allowlist.

## Non-negotiable constraints

- **No network access at runtime.** Nothing shipped downloads anything; telemetry is off everywhere (`OPENSPEC_TELEMETRY=0`).
- **No npm install scripts in shipped artifacts** (build with `--ignore-scripts`); no new runtime dependencies beyond Node (Route A) and the Python standard library (the Python check).
- Keep OpenSpec's MIT license/copyright in `THIRD_PARTY_NOTICES.md`; never present this as an official OpenSpec or Palantir product; "Palantir"/"Foundry" are their trademarks — note that in the README.
- No Palantir proprietary content, customer data, or credentials anywhere, including test fixtures.
- The artifact graph (see Architecture) is fixed by the forked schema — don't reorder it when editing templates or skills. Adding an artifact changes it: ask first.
- Ask before: changing the artifact order, adding a dependency, or making any network call outside the build step.
